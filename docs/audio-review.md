# Task 2 independent review

Verdict: changes required. Reviewed the review package, current Windows source, Core contracts, and existing windows-tests.json. Existing evidence is 6/6 passing groups, hardwareRequested=false. No tests or hardware capture were rerun; no product files were changed.

## Actionable findings

1. **P1 — Await capture termination before completing/disposal** (`prototype/src/AntiDbt.Windows/AudioSources.cs:67-68`). StopAsync calls StopRecording, immediately Finish, and returns a completed task. The installed NAudio.Wasapi 2.3.0 XML explicitly describes StopRecording as a stop request and says to wait for RecordingStopped to know capture finished. Therefore the source announces completion while capture is still running; final callbacks are discarded by finished, and a later capture exception is hidden by the earlier successful Finish. Dispose also proceeds without a source-level completion barrier. Track RecordingStopped with a completion task, await it with the supplied cancellation token, and finalize from that event. Verify with a deterministic delayed-stop callback fixture and retain hardware smoke as a separate unrun gate.

2. **P2 — Dispose the WAV reader when startup validation fails** (`prototype/src/AntiDbt.Windows/AudioSources.cs:74`). WaveFileReader is constructed before StreamingPcmConverter; if converter construction rejects a readable unsupported format (for example 8-bit PCM), the reader never enters the pump using scope. Stop/Dispose cannot reach that local reader, leaving the file handle open until finalization. Wrap startup acquisition in try/finally or transfer ownership only after all initialization succeeds. Verify unsupported-format startup followed by exclusive file reopen.

3. **P2 — Serialize lifecycle transitions and make disposal terminal** (`prototype/src/AntiDbt.Windows/AudioSources.cs:63-68,72-76`). The feed lock does not protect Start/Stop/Dispose. For example, disposing an unstarted source completes its channel but leaves started=false/lifetime=null; a later Start succeeds and acquires capture/file resources even though every Feed is discarded. Concurrent Start/Dispose can also register cancellation after disposal or replace/read capture while it is being disposed. WaveFile Dispose leaves a disposed lifetime field, so repeated Dispose/Stop invokes Cancel on a disposed CTS. Introduce a small synchronized lifecycle with a terminal disposed state, reject start after disposal, and make stop/dispose idempotent; verify those interleavings without hardware.

4. **P2 — Advance the audio clock for ring-dropped samples** (`prototype/src/AntiDbt.Windows/AudioSources.cs:52-53`). Feed writes all converted output into the 640000-byte drop-oldest ring before draining it, but samples advances only for emitted bytes. A single feed producing 22 seconds of PCM retains the newest 20 seconds and labels the first retained chunk AudioStart=0 rather than 2 seconds. The standalone ring test checks retained bytes, not the source clock after overflow. Report dropped sample count from the ring and advance samples before emitting; verify with one oversized synthetic Feed. Normal WAV reads and typical WASAPI callbacks are smaller, so this is the required overflow path rather than evidence of routine loss.

## Compliance and evidence limits

- Capture construction and enumeration use render endpoints and WasapiLoopbackCapture; system loopback is preserved. No microphone source or audio persistence was added.
- Converter phase/weighted area and incomplete-frame remainder persist across callbacks. Signed PCM 16/24/32 decoding, floating point downmix, nonfinite handling and S16LE clipping look consistent. Current callback-invariance coverage uses only 48 kHz; PCM-width checks use silence only. Nonzero signed 24/32-bit vectors and 44.1 kHz split-input/rate vectors would substantiate the broader claims. The box/area filter limitation is accurately disclosed.
- The 50-entry channel uses DropOldest and emitted sample positions correctly preserve channel-drop gaps. Ring operations preserve whole samples at public boundaries; the separate ring-overflow clock issue is above. Tail chunks are shorter than 6400 bytes as disclosed.
- ApiKey and Secrets fields are JsonIgnore in Core, and both providers' values are encrypted using DPAPI CurrentUser before serialization. No plaintext secret persistence was found. Managed UTF8/native plaintext buffers are cleared, although immutable secret strings necessarily remain in application memory.
- Settings uses a single same-directory temporary envelope, flushes it, and replaces settings.json, avoiding cross-file generation mismatch. Invalid JSON/version/ciphertext recovers to defaults with Warning. Options are serialized. Existing test covers JSON corruption and DPAPI roundtrip, not ciphertext/version corruption or filesystem fault injection.
- Minor resilience concern: SettingsStore.cs:85 executes File.Delete before gate.Release in the same finally; a cleanup exception would permanently retain the semaphore. A nested finally should guarantee release. This requires an I/O-failure path and was not reproduced.
- Hardware capture, endpoint removal, real provider audio quality, and concurrent lifecycle behavior remain unverified. Existing passing synthetic tests do not establish those properties.
