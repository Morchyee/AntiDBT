# Follow-up Windows, Core and Desktop review

Verdict: Windows fixes address the previous findings; Core/Desktop still need changes below. This was source/artifact review only, with no tests rerun or implementation edits. Current artifacts report Core 23/23 and Windows 16/16, including hardwareRequested=true and a passing hardware-capture-smoke entry. That hardware result is read from the producer artifact, not independently exercised by this review; it does not establish transcription quality.

## Remaining actionable findings

1. **P1 — Request failure discards a queued newer/final revision** (`prototype/src/AntiDbt.Core/TranslationScheduler.cs:67-73`). The exception handlers surround the entire job loop. If revision 1 is in flight, revision 2 updates Latest, and revision 1 fails or times out, the catch tries to mark revision 1 errored (the store rejects that stale revision) and finally removes the job. Revision 2 is never requested and can remain pending forever if it was final. Handle request errors inside the loop, then atomically compare Latest and continue when newer work exists; only terminate when the failed request is still current or cancellation is requested. Test delayed failure and timeout with a newer final revision already queued, asserting revision 2 is translated.

2. **P1 — Concurrent UI stop paths can clear a newer pipeline and invalidate its generation** (`prototype/src/AntiDbt.Desktop/MainWindow.cs:40,84-85`; `prototype/src/AntiDbt.Core/CaptionPipeline.cs:146`). Busy guards exist on start/settings but not language switch, demo or StopCaptureAsync itself. During one stop, a second stop calls DisposeAsync, which returns immediately because _disposed was set before the first disposal completed. The second stop sets pipeline=null and busy=false, allowing a new session. The first stop later sets pipeline=null again; its Store.BeginSession(false) can also invalidate the new session in the shared store. Serialize all capture lifecycle entry points, await one shared disposal task, capture the pipeline reference being stopped, and clear it only if still current. Add a delayed audio-stop fixture and overlap Stop/demo/language actions; assert the new session cannot be erased or invalidated.

3. **P2 — Disposal failure permanently prevents resource cleanup retry and escapes UI handlers** (`prototype/src/AntiDbt.Core/CaptionPipeline.cs:146-147`; `prototype/src/AntiDbt.Desktop/MainWindow.cs:84,103-106`). Pipeline marks _disposed before cleanup. If audio disposal times out (the new Windows source explicitly leaves the session alive for retry), scheduler/lifetime disposal is skipped and a later pipeline Dispose returns immediately. MainWindow StopCaptureAsync has finally but no catch, so this timeout also escapes async-void click/closing handlers as an unhandled dispatcher exception. Preserve/reuse a completion task, guarantee independent cleanup in finally blocks, allow the audio cleanup policy to retry, and catch/report stop failures at UI boundaries. Verify a first-dispose failure followed by successful retry and safe window close.

4. **P2 — Expanded view presents draft translations without their pending label** (`prototype/src/AntiDbt.Desktop/MainWindow.cs:96-100`; `prototype/src/AntiDbt.Core/SubtitleProjection.cs:33-36`). Projection uses ProvisionalTranslationText when no exact translation exists, but the expanded DataTemplate binds only Translation and ignores TranslationPending. Compact mode correctly adds an updating label. In history, an older-revision draft is therefore presented as an exact translation of the corrected source. Bind a pending/error indicator in expanded rows too, and verify a source correction with retained draft in both modes. Also distinguish failed/stopped pending rows from actively updating ones rather than permanently showing an active-progress label after cancellation.

5. **P2 — Settings save failure is immediately overwritten by a success message** (`prototype/src/AntiDbt.Desktop/MainWindow.cs:62,66`). SaveSettingsAsync catches disk/permission failures and sets an error status, but OpenSettingsAsync unconditionally replaces it with settings-saved after the call returns. Return a success result or allow the caller to handle failure; only display success after persistence succeeds. Test an unwritable/failing settings store.

## Fixes that look correct

- Windows stop waits for RecordingStopped before completing chunks, lifecycle is serialized, start-after-disposal is rejected, repeated WAV disposal does not cancel a disposed CTS, failed WAV initialization releases the reader, and ring dropped samples advance AudioStart.
- Settings cleanup now releases its semaphore in nested finally even when temporary-file cleanup fails. New test source covers the previously missing signed PCM/44.1 kHz and malformed version/ciphertext cases.
- Scheduler success path compares Latest and removes a completed job under the same lock, avoiding the lost-update window on successful completion. Fixed coalescing windows avoid debounce resets; WaitAsync on provider tasks releases logical slots on timeout/cancellation, and eventual task faults are observed.
- Exact and provisional translation fields are distinct and revision/session guarded. Compact projection now preserves multi-segment sentence prefixes. Nine-second stop budget fixes the previous guaranteed three-second truncation of normal ASR/MT drains; large paced backlogs can still exhaust a bounded budget as an intentional limit.

## Secondary gaps

- IsDeleted handling removes a row but retains no tombstone revision. A later stale same-session source result can recreate the deleted row. Current provider results are serial; retain a bounded tombstone revision map if the Core contract intends to reject all stale callbacks after deletion, and test deletion followed by an older source event.
- Pipeline reader tasks are still canceled without a bounded join in connection cleanup; reconnect tests should check eventual task faults and source/session disposal together.
- The new fixed-window scheduler can create detached requests if a plugin ignores cancellation. Logical jobs are capped but actual outstanding uncooperative calls are not; this is a plugin-resource limitation, distinct from the now-fixed semaphore starvation.
